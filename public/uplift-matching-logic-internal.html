How matching actually works.

The real scoring logic behind founder–mentor pairings, so anyone on the team can explain it accurately, debug a weird match, or update it responsibly. Every number here is read directly from the code, not summarized from memory — file:line citations throughout.

Two systems exist. Only one is live for Fall.

These produce different tier labels and work completely differently. Don't mix them up when talking to anyone about "the algorithm."

The Fall scoring formula

Every mentor gets scored against every founder. Session commitment is weighted heaviest by design — the code comment states pairs "only work when both sides expect the same amount of time together." scoreMentor(), pages/admin-fall.js:38–71.

FactorHow it's checkedPoints
Session commitment Mentee's requested tier vs. mentor's offered tier, banded into 3 / 4–6 / 7–10 sessions (tierBand(), :17–23) +4 exact band
+2 mentor offers more
−2 mentor offers fewer
Focus area overlap Mentee's topics/primary focus vs. mentor's focus areas, matched against a fixed 16-word keyword list (FOCUS_KEYWORDS, :9) +2 per keyword
(max 3 counted = +6)
Shared language Words ≥5 characters (stopword-filtered) in mentee's "hoping"/"value sought" vs. mentor's "why"/"give" free-text fields +2 for 2+ shared words
+1 for exactly 1
Stage fit First word of mentee's stage found in mentor's stated stage preferences +2
Schedule overlap Mentor lists "flexible," or mentee/mentor share a morning/evening/weekend keyword in time preference +1

Tiers

gradeOf(score), pages/admin-fall.js:30–36

Perfect matchscore ≥ 11Top of the range — strong alignment across nearly every factor.
Excellent matchscore ≥ 8Strong alignment on most factors, typically including session commitment.
Strong matchscore ≥ 6Solid overlap, usually missing one dimension.
Good matchscore ≥ 3Workable, but worth a second look before confirming.
Weak matchscore < 3Low signal overlap — usually only surfaces when better options are exhausted.

Note: these are the real labels. "Excellent / Great / Strong / Good / No match" has circulated informally but doesn't match the code — there's no "Great" tier and no "No match" tier, and the bottom tier is "Weak," not "No match."

The human step

Scoring never finalizes a match by itself. Ranked mentor candidates are shown per founder in the admin UI; a person reviews the list and reasons, then clicks to confirm a pairing. That click calls doMatch() (admin-fall.js:236–241), which POSTs to pages/api/admin/fall-match.js:31–58 — a pure Google Sheets append. No scoring or auto-selection happens server-side; the endpoint only records what a human already decided.

What this doesn't do (yet)

⚠
No industry or geography factor. Despite being a common assumption, industry alignment and NJ county/location are not scored anywhere in this formula. County appears in the admin UI for reference (admin-fall.js:313, 328) but doesn't affect the match score.
⚠
Focus-area matching is keyword-based, not semantic. It only recognizes the 16 fixed terms in FOCUS_KEYWORDS — a mentee and mentor describing the same need in different words (e.g. "runway" vs. "fundraising") may not register as overlap unless the exact keyword appears.
ℹ
The Summer LLM tool did consider industry. Its prompt explicitly told the model to prioritize "industry alignment → focus area alignment → stage fit → NJ county proximity" (suggest-matches.js:82) — that ordering does not carry over to the Fall scorer, which is a different system entirely.
